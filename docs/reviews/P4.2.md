# P4.2 - CI workflow

Row: `- [~] (B) P4.2 - CI workflow running the check gate on every push and pull request (plan: Checks)`

Tier: B

## Why

The plan's Checks section makes CI the confirmation of the local gate and a required status
check on `main`, so the repository needs a workflow before any other package can land through a
pull request. `ci.yml` runs the eight checks of `scripts/check.ts` in the same order under the
same names, so a local `pnpm check` and CI cannot disagree about what was run; it is also callable
(`workflow_call`) so the release workflow can run the same job on a tag. Node is pinned to the 22
line, the plan's floor, and a guard step fails clearly if the runner's 22.x is older than the
22.22 Astro requires. `check:e2e` installs Chromium first; `pnpm test:e2e` already builds the
package and the three demo variants. The demo builds are uploaded on every run and Playwright's
`test-results` (traces kept on failure; the reporter is `list`, so there is no HTML report) on
failure. The workflow has read-only repository permissions and needs no secret.

Acceptance, completed by the maintainer: the workflow runs on this package's pull request and
after its squash merge, both runs green end to end including e2e, and the `checks` job is then a
required status check on `main`.

### Findings

No P1 or P2 findings.

- **P3 - concurrency group can collide with the caller.** In `ci.yml`, the concurrency group
  is `${{ github.workflow }}-${{ github.ref }}`. In a reusable workflow the `github` context belongs to
  the caller, so under `workflow_call` this evaluates to the release workflow's name and the tag
  ref. If P4.3 gives `release.yml` a workflow-level concurrency group built the same way, the
  called workflow and its caller share one group and GitHub cancels the run as a concurrency
  deadlock. Smallest fix: use a literal prefix here (`group: ci-${{ github.ref }}`), or make P4.3
  avoid the same expression; worth settling before P4.3 is written.
- **P3 - superseded runs on `main` are cancelled.** `cancel-in-progress: true` also applies to
  pushes to `main`, so two merges in quick succession leave the first merge commit without a
  completed `checks` run, while the Releases steps say to tag a merge commit whose CI on `main`
  is green. Consider `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`.
- **P3 - actions referenced by mutable major tags.** For a public repository whose workflow is
  later called by the publishing workflow, pinning each action to a full commit SHA (with the
  version in a comment) removes the risk of a moved tag. Advisory; the job itself has read-only
  permissions and no secret.
