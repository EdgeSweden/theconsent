# P3.2 - Gate: module-script ordering

Row: `- [~] (A) P3.2 - Gate: keep page order for module scripts, inline and external (plan: Script gating)`

Tier: A

## Why

The post-release review reported that a gated inline module ran after the classic script that
followed it, contrary to the README's "page order" promise, and that `nomodule` was applied to
module scripts. A Chromium regression test (`test/e2e/gate-order.spec.ts`, serving the built
package through request interception with its own strict hash CSP) reproduced the observation, and
two probes established why: an inserted inline module fires no `load` event, so no script can wait
for it, and browsers do order modules inserted with `async = false`. Without gating, modules are
deferred too, so a classic script after a module runs first. The v0.2.0 runtime already produced
that native order (the new browser tests pass against it); the defect was the README's single
"page order" claim. This package states the real contract (decision #54), simplifies the gate to
it (modules always `async = false`, never waited for; `nomodule` only for classic scripts) and pins
it with browser tests: classic order, module order, a module after a slow module, `nomodule`
handling. Renaming the row's intent from "keep page order for modules across kinds" to "native
order" is therefore deliberate.

### Findings

**P2 - A gated external module blocks every later gated classic script, contrary to decision #54
and the CHANGELOG.**

- Location: `src/gate/index.ts`, `activate`: `live.async = isAsync;` for external classic scripts
  without `async`.
- Requirement: decision #54 ("the order a page without gating would have ... modules ... never
  waited for"); CHANGELOG Unreleased: "Modules are always inserted with `async = false` and never
  block later scripts"; README: "a classic script after a module may run before it".
- Failure: a module and an external classic script both inserted with `async = false` join the
  same "list of scripts that will execute in order as soon as possible" (HTML, prepare the script
  element), so the classic script waits for the module. The gate then waits for that classic
  script's `load` before inserting anything after it, so a slow or hanging module holds up every
  later gated classic script, inline ones included. Reproduced in Chromium against the built
  package (scratch probe, placeholders: external module served after 800 ms, external classic,
  inline classic):
  - gated: at ~150 ms `[]`; at ~1.6 s `["slow module","ext classic","inline classic"]`;
  - same page without gating: at ~150 ms `["ext classic","inline classic"]`, module last;
  - module request that never completes: gated runs nothing at all; native runs both classics.
    A site gating a module from a slow third-party host followed by a classic tag and its inline
    init therefore gets the classic scripts delayed or never run, which is the opposite of what the
    package now documents.
- Smallest safe fix: insert classic scripts as async (`live.async = isAsync || classic;`). Their
  order is already enforced by the chain, which waits for each external classic script's
  `load`/`error` before inserting the next, so they stop joining the browser's ordered list
  shared with modules; modules keep `async = false` and stay ordered among themselves. Verified in
  the same probe: with this one change the gated order equals the native one in all three cases.
- Regression test: an e2e case in `test/e2e/gate-order.spec.ts` with a slow external module
  followed by an external classic script and an inline classic script, asserting both classic
  entries are logged before the module (ideally also a module that never responds, asserting the
  classic scripts still run). A unit assertion that a live classic external script has
  `async === true` while modules have `async === false` pins the mechanism.

**P3 - Row intent changed without the board annotation.** The review file says the row's intent
("keep page order for module scripts ... across kinds") is deliberately narrowed to native order
by decision #54, but the `[~]` row is not annotated `decision taken, see #54` as Delivery >
Authority order asks.

**P3 - Weak unit assertion.** `modules are inserted with async false and never waited for` checks
`liveModules.length >= 2`; it should assert the exact count (2) so a dropped module fails.

### Review 1 findings

- P2 (external module blocks later classic scripts): resolved. `activate` now sets
  `live.async = isAsync || classic`, so classic scripts never join the browser's in-order list;
  the chain still waits for each external classic script without `async`, and modules alone keep
  `async = false`. Decision #55 records the supersession of #44's `async = false` part. The two new
  e2e cases (slow module, never-answering module, each before an external and an inline classic
  script) were confirmed in a scratch copy to fail with the Review 1 assignment restored (2 of 6
  failed) and pass with the fix. The unit tests pin the mechanism (`async === true` for a live
  external classic script, `async === false` for every live module).
- P3 (board annotation): resolved; the row carries `decision taken, see #54`.
- P3 (weak unit assertion): resolved; the test asserts exactly 3 live modules (the two added plus
  the fixture's own), which fails if one is dropped.

### Regression surface checked

- Inline classic scripts: `async` is ignored for inline scripts, so they still run on insertion in
  chain order; the native-order e2e case covers slow external classic -> inline -> fast external ->
  inline.
- Skipped scripts (`nomodule` classic, unknown type) are not classic, get `async = false` and are
  not waited for; the browser never prepares them, so they cannot enter the in-order list. Covered
  by the `nomodule` e2e case.
- Type matching: `kind` is lower-cased before `CLASSIC_TYPE`, so dropping the `/i` flag is safe;
  `module` in any case is treated as a module.
- No change to when activation happens (only after a grant, or at mount for required
  categories), so no optional I/O before a choice; no new inline code or HTML-string API in
  `src/gate`, so CSP is unaffected.
