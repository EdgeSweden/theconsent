# P1.1 - Config schema + validateConfig

Row: `- [~] (A) P1.1 - Config schema + validateConfig, one test per rule (plan: Config, Validation)`

Tier: A

## Why

The config is the package's contract with every site, and the build is the only place a bad
config can be stopped before a visitor sees it. The schema is written once in zod with strict
objects at every level so unknown keys fail, and the TypeScript types are derived from it so the
documented interface and the runtime check cannot drift. Cross-field rules (ids, locale coverage,
link tokens, the mandatory Accept all / Reject all, blocking requires a dimmed backdrop, colour
parsing and contrast) run after the structural parse and name the offending key. The core imports
only types from this code, so zod stays out of the browser bundle. Contract gaps the plan left
open are settled in decisions #11 to #16.

## Review 1

Reviewed `git diff main...feat/config-schema` against plan sections Config, Validation, Version
boundary, Safety and Delivery, and decisions #11 to #16. `pnpm check` re-run on the branch: all
checks green (205 unit tests, e2e 1). Probes were run in a scratch copy outside the repository.

### Findings

**P2-1. Record URL check accepts a scheme-relative URL via stripped tab/newline.**

- Location: `src/astro/validate.ts`, `isAllowedRecordUrl` (root-relative branch).
- Requirement: plan, Validation: "`record`, when a string, is a root-relative path (`/…`) or an
  absolute `http(s)` URL; any other scheme or a scheme-relative URL fails."
- Failure scenario: `record: "/\t/collector.example/c"` (or `"/\n/…"`) passes because only the
  raw prefixes `//` and `/\` are rejected. The WHATWG URL parser strips ASCII tab and newline, so
  `sendBeacon`/`fetch` resolve it to `https://collector.example/c`: records go cross-origin while
  the build reports the config as same-origin. Probe: `validateConfig` returns `ok: true`;
  `new URL("/\t/evil.example/c", "https://site.example/").href` is `https://evil.example/c`.
- Smallest safe fix: resolve rather than prefix-match. For a string starting with `/`, require
  `new URL(url, "https://base.invalid/").origin === "https://base.invalid"`; for the absolute
  branch the existing `new URL` protocol check plus a raw `^https?://` test is fine, but reject
  any input containing ASCII tab, LF, CR or C0 controls outright for both branches.
- Regression test: add `"/\t/example.com/c"`, `"/\n/example.com/c"` and `"/\r/example.com/c"` to
  "other schemes, scheme-relative and relative URLs fail".

**P2-2. Link href scheme check is bypassable; `javascript:` hrefs pass validation.**

- Location: `src/astro/validate.ts`, `isAllowedHref`.
- Requirement: decision #16 (authority level 2): link `href`s are relative or use `http`,
  `https`, `mailto` or `tel`, to close a way a config could inject a script URL.
- Failure scenario: `"java\tscript:alert(1)"`, `"jav\nascript:alert(1)"` and
  `"\x01javascript:alert(1)"` all pass (the regex sees no scheme, so they are treated as
  relative), yet the URL parser resolves each to protocol `javascript:`. When P1.4 renders
  `{link:<id>}` as `<a href>`, the click runs script; under the demo's strict CSP it is blocked
  and reported as a violation, on a CSP-relaxed site it executes. The rule the decision promises
  is not enforced.
- Smallest safe fix: determine the scheme the way the browser will:
  `new URL(href, "https://base.invalid/").protocol` must be one of `http:`, `https:`, `mailto:`,
  `tel:` (a relative href resolves to `https:`); optionally also reject C0 controls/tab/newline.
- Regression test: add the three strings above to the `bad` list in "link hrefs may not use a
  script-capable scheme".

**P3-1. An empty `title` with no `dialogLabel` validates.** `localeStrings.title` is
`z.string()`, so a locale can produce a dialog with no accessible name (plan: Accessibility,
`aria-labelledby` the title or `aria-label` from `dialogLabel`). Decision #16 states the extra
non-empty rules exist to prevent unlabelled controls; consider failing when `title` is empty (or
whitespace) and `dialogLabel` is absent, with a test.

**P3-2. The colour parser accepts some syntax browsers reject.** e.g. legacy comma syntax mixing
numbers and percentages (`rgb(50%, 10, 20)`) parses, so contrast is checked against a value the
browser will treat as invalid. Low impact; either tighten the legacy branch or note it in
decision #14.

### Questions

- `validateConfig` returns early on any schema error, so cross-field errors (ids, locales,
  contrast) appear only after the structural errors are fixed. Intended? It is consistent with
  "a failure names the offending key", just a two-pass experience for the site author.

## Review 2

Targeted re-review of the Review 1 fixes (`c11cda9`) and their regression surfaces

### Status of Review 1 findings

- **P2-1 resolved.** `isAllowedRecordUrl` now rejects backslashes, ASCII controls and spaces
  outright and resolves the URL: a `/`-prefixed value must resolve to the probe origin, anything
  else must be a raw `http(s)://host` URL with an `http(s):` protocol. Probes: `"/\t//…"`,
  `"/\n/…"`, `"/\r/…"`, `"/ /…"`, `" /c"`, `"/c "`, `"https:example.com"` fail; `"/consent"`,
  `"/c?x=1#y"`, `"/..//example.com"` (resolves same-origin), `"HTTPS://example.com/c"` pass.
  Regression tests added.
- **P2-2 resolved.** `isAllowedHref` rejects ASCII controls and decides by the protocol the URL
  parser resolves, so it agrees with what the browser will do. Probes: `"java\tscript:"`,
  `"\x01javascript:"`, `"javascript\r:"`, `" JavaScript:"`, `"JaVaScRiPt:"` fail; inputs the
  parser treats as relative (`"javascript%3Ax"`, `"​javascript:x"`) resolve to `https:` in
  the browser too and are harmless. Regression tests added.
- **P3-1 resolved.** An empty or whitespace-only `title` without `dialogLabel` fails at
  `locales.<code>.title`; `dialogLabel` is already non-empty by schema. Positive and negative test
  added.
- **P3-2 resolved** for the reported case (`rgb(50%, 10, 20)` now fails, test added).
- **Question resolved** by decision #17 (structural errors first, then cross-field rules).

**P3-1. Two more legacy-syntax colours parse that browsers reject.** `rgb(none, 10, 20)` (legacy

Same class and impact as Review 1 P3-2; tighten the legacy branch (no `none`; `%` for the `hsl`
