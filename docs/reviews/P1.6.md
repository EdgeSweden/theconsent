# P1.6 - Astro integration

Row: `- [~] (B) P1.6 - Astro integration: build-time validation, virtual module, injected script (plan: Astro integration)`

Tier: B

## Why

The integration is what turns "config is the contract" into a build failure: it imports the
site's config module at build time, runs `validateConfig`, logs contrast warnings and throws with
every offending key before Astro bundles anything. The browser receives the config through a
virtual module that re-exports the site's own module, so a function `record` survives (a JSON
copy would drop it). The demo now uses the integration, so `check:e2e` proves the real path: the
built page mounts the banner, links the stylesheet and records zero CSP violations under Astro's
hashed CSP with `default-src 'self'`. Building the demo surfaced that Astro does not link CSS
imported from a `page` script, hence the `page-ssr` stylesheet import (decision #35).

### Findings

No P1. No P2.

- **P3** `package.json` `engines.node: ">=22"` vs `src/astro/integration.ts` `loadConfig`: the
  documented `consent.config.ts` form relies on Node's native type stripping (Node >= 22.18, per
  decision #34). With the allowed peer range (`astro >= 5`) a site on Node 22.0 to 22.17 gets
  `ERR_UNKNOWN_FILE_EXTENSION` at build time. Loud, not silent; either raise `engines` to
  `>=22.18` or state the requirement in the README (P1.8).
- **P3** `loadConfig` uses Node's resolver while the browser bundle uses Vite's: extensionless
  relative imports, tsconfig path aliases, `import.meta.env` or non-erasable TS syntax in the
  config (or its imports) fail at build time although Vite would accept them. Document these
  constraints next to the config reference in the README.
- **P3** Dev only: `addWatchFile` and the `?t=` cache-buster cover the root config file only. An
  edit to a module the config imports is not re-validated (and Node keeps the stale copy across
  restarts), while the browser receives the new values via Vite. Builds are unaffected.
- **P3** The page script's `@edgesweden/consent` import also carries the core's `styles.css`
  import, so besides the linked `index.*.css` Astro emits an identical, unreferenced
  `page.*.css` asset. Harmless; worth a comment next to decision #35.
- **P3** Decision #36 records existing `src/core/runtime.ts` behaviour that this diff does not
  touch; fine as a durable fact, but it is outside this package's scope.
