# P4.0 - Operating contract for the public repository

Row: `- [~] (A) P4.0 - Operating contract for the public repository: CI, pull requests, tag-driven staged releases, read-only git for agents, no tooling references (plan: Delivery, Checks, Releases, Repository layout)`

Tier: A (this operating contract; releasing)

## Why

The maintainer decided to publish the package from a new public repository,
`EdgeSweden/theconsent`, with CI, pull requests and tag-driven staged npm releases, and to publish
0.3.0 as the first npm version of this codebase. The plan still described a local-only process
with no remote, no CI and no publishing, and by its own authority order every later package of
that work would have conflicted with it, so the contract is amended first and reviewed as a plan
change. The amended Delivery, Checks, Releases and Repository layout sections describe the target
state: a protected linear `main`, squash-merged pull requests, the check gate in CI, releases from
pushed tags through a staged, provenance-attested publish approved with 2FA, git read-only for
implementers and agents, review by someone without the implementer's context, and no tool or model
names, session descriptions or attribution trailers anywhere in the repository. The operating
contract stays in `docs/plan.md`; `AGENTS.md` points at it, and the root pointer file for the
maintainer's own tooling now only names `AGENTS.md`. Package metadata points at the new
repository. Decisions #60–#65 record the maintainer's decisions in the form the maintainer
supplied; the Astro peer-range decision is recorded with the package that changes the range
(P4.4). The board gains rows P4.0 and P4.2–P4.7; the import of the tree into the public repository between P4.0 and P4.2
is a maintainer step and has no row.

Maintainer acceptance for this package: a search of the tree for AI tool, vendor and model names
and for attribution trailers returns only the root pointer file; a search for the previous
repository URL and other repositories' names returns nothing; no section still describes a
remote-less or CI-less process.

## Review 1

Reviewed `git diff main...docs/public-repository` against the amended `docs/plan.md` and
`git show main:docs/plan.md`. The tree search the acceptance criteria name was run on the branch:
tool, vendor and model names match only the root pointer file (by name; its content is
`@AGENTS.md`), there are no attribution trailers in tracked files, and the previous repository URL
and directory name no longer appear.

### Findings

- **P2** `docs/plan.md`, Releases (release steps) together with Roles and Package flow steps 4–8:
  the release pull request requires `pnpm release:check` green, and `release:check` refuses a
  dirty working tree outside CI. Under the amended contract the implementer cannot commit, so the
  implementer's tree for a release package (P4.7) always carries the uncommitted version bump and
  CHANGELOG move, and `release:check` can never pass before handoff. Failure scenario: the P4.7
  implementer either reports a red gate it cannot fix, or weakens the clean-tree rule to get a
  green run, which changes a Tier A release gate as an incidental fix. Violated requirement: the
  release steps must be executable by the roles the plan defines. Smallest fix: state who runs
  `release:check` and where, e.g. "the implementer runs `pnpm release:check --allow-dirty` (or the
  clean-tree rule is reported, not enforced, before commit); the full check runs green in CI on
  the pull request and on the tagged commit", or assign the local run to the maintainer after
  committing. Check: the P4.3/P4.7 review confirms the stated procedure runs green from an
  uncommitted implementer tree and from a clean CI checkout.

- **P2** `docs/plan.md`, Status, Releases ("tagged but never published"), Branches, pull requests
  and commits ("Nobody ... moves or deletes a tag") and Public repository neutrality ("no
  attribution trailers ... in ... commit messages"): the plan does not say how the existing
  history and the local tags `v0.1.0`–`v0.2.2` reach the public repository, and the review file
  says the history import is a maintainer step with no row. The local history carries 17
  attribution trailers, including on tagged commits. Failure scenario: pushing the history as it is
  breaks neutrality in commit messages; rewriting it and re-creating the tags on the rewritten
  commits moves tags, which the plan forbids. Either way the maintainer acts against the plan, and
  the P4 slice list skips P4.1 without saying why. Smallest fix: one sentence in Status or
  Releases, plus a decision entry, that settles the import, for example: "The public repository
  starts from an import of `main` with commit messages rewritten to satisfy Public repository
  neutrality; the local tags `v0.1.0`–`v0.2.2` are not pushed, and the tag rules apply to tags in
  the public repository", and a line saying the import (P4.1) is a maintainer step with no board
  row. Check: re-review confirms the plan states the import and nothing in it conflicts with the
  tag and neutrality rules.

- **P3** `docs/plan.md`, Checks: "Node 22 (at least 22.18 ...)" gives the type-stripping floor,
  but the dev toolchain needs more: decision #3 records that Astro 7, which `check:e2e` builds
  with, requires Node >= 22.22, and Astro 7.4.1 declares `>=22.22.0`. A CI matrix pinned to the
  stated floor would fail at `check:e2e`. Suggest "at least 22.22 (Astro 7 requires it; repository
  scripts need 22.18 type stripping)", and use that floor in P4.2.

- **P3** `docs/plan.md`, Releases: "skipped in CI, where the checkout is clean by construction"
  leaves the clean-tree check out even after install and build, which is when it would catch a
  build or install step that changes tracked files (for example a lockfile drift that
  `--frozen-lockfile` is supposed to stop, or a generated file that is checked in). With `dist/`
  ignored, running the clean-tree check in CI after build costs nothing. Advisory for P4.3.

- **P3** `docs/plan.md`, Package slices, P0 row: it now says P0 delivered `AGENTS.md`, but P0
  delivered the pointer file that P4.0 rewrites; the row is history. Leaving it as written, or
  saying "the root pointer file (`AGENTS.md` from P4.0)", would keep the slice list accurate.

### Questions

- Releases and Safety name a staged publish (`npm stage publish`, a stage-only trusted publisher,
  approval with 2FA). P4.3 should confirm the exact npm command, the minimum npm CLI version and
  the trusted-publisher fields against npm's documentation at implementation time; the plan
  wording should follow what npm actually offers.
- The release workflow "runs the full CI workflow on the tagged commit" and checks the commit is
  an ancestor of `origin/main`; that needs a full-history checkout (`fetch-depth: 0`) of `main` in
  the release job. Presumably a P4.3 detail; worth naming in `docs/releasing.md`.
- This review was briefed with `git diff main...<branch>` on a committed branch, as the previous
  contract prescribed; the amended Review section prescribes `git diff main` with
  `git status --short` or the pull request's diff from P4.0 on. No action needed for this package.

Verdict: changes required

## Review 2

Targeted re-review of the Review 1 findings and the passages they touch, using
`git show docs/public-repository` (the fix commit) and the amended `docs/plan.md` on the branch
(Status, Checks, Releases, Package slices, Roles, Branches, pull requests and commits, Package

Review 1 findings:

- P2 (release:check before commit): resolved. Releases now assigns `pnpm release:check` to the
  maintainer after the release branch is committed and has the release workflow run it again on
  the tag. That matches Roles (the maintainer commits from the implementer's working tree) and
  Package flow steps 8–10, and the clean-tree rule is unchanged, so P4.7 has no reason to weaken
  the gate.
- P2 (history import and local tags): resolved. Releases and decision #65 state that the public
  repository starts from one import commit of the tree, the local history and the tags
  `v0.1.0`–`v0.2.2` are never pushed, and `v0.3.0` is the first public tag, with the tag rules
  applying to the repository a tag is pushed to. No tag is moved and no commit message with an
  attribution trailer reaches the public repository, so the tag rules and Public repository
  neutrality no longer conflict. Package slices explains the P4.1 gap as a maintainer step with
  no board row, and `docs/progress.md` has no P4.1 row, which agrees.
- P3 (Node floor): resolved; Checks now says 22.22.
- P3 (P0 row): resolved; it now says "the agent pointer file".
- P3 (clean-tree check in CI after build): not taken up; still advisory for P4.3.

### Findings

- **P3** `docs/reviews/P4.0.md`, Why: "the public history import between P4.0 and P4.2" now
  contradicts decision #65, which imports the tree without the history. Suggest "the import of
  the tree into the public repository". The squash body comes from this _Why_, so it is worth
  fixing before commit.
- **P3** `docs/plan.md`, Releases and Package slices: "the tree at 0.2.2" could be read as the
  `v0.2.2` tag's tree. The import happens after P4.0 merges, so the imported tree contains this
  amended plan while `package.json` still says 0.2.2. "the tree of `main` after P4.0 (version
  0.2.2)" would remove the ambiguity.

### Questions

- For a release package, `release:check` runs only after review and handoff, so its result cannot
  be in the review file. If it fails on the committed branch, the fix is a change after the
  review handoff and needs targeted re-review under Review. That looks intended; P4.3's
  `docs/releasing.md` could say so.

Proposed squash-commit subject: `docs: amend the operating contract for the public repository`
