# P4.6 - Hardening: late content stays inert, unique id prefix, theme.vars runtime guard

Row: `- [~] (A) P4.6 - Hardening: late content stays inert, unique id prefix, theme.vars runtime guard (plan: Accessibility, Validation, CSP)`

Tier: A (blocking-mode non-dismissability, validation enforced at runtime, the size budget)

## Why

Three small gaps in guarantees the plan makes. Blocking mode makes the rest of the page inert,
but only the body children present when the dialog opened: a single-page app or a late widget
appended to `body` while the banner was open stayed interactive, and a host script that removed
`inert` re-enabled the page. One `MutationObserver` on `body` while a blocking dialog is open now
re-applies `inert` to such children (host-owned `inert` is still left alone), and frees the page
if the host removes the banner root; it is disconnected on close and on teardown. The banner used
fixed ids, so a host element with the same id captured `aria-labelledby`, `aria-describedby` or a
label's `for`; the UI now uses the first of `consent-`, `consent1-`, … that no element in the
document uses when it is built, so the default ids are unchanged. `theme.vars` were applied
unguarded, so `mount` with an unvalidated config could set a colour token and bypass the contrast
rule; they are now filtered at runtime the way validation filters them. The token list would
not fit the budget, so the filter is a pattern equal to the colour tokens' property names, held
equal to `THEME_COLORS` by a unit test. The core plus stylesheet measures 5,997 of 6,000 bytes
gzipped after all three (was 5,746); decision #69.

### Findings

No P1 or P2 findings.

- **P3** `src/core/banner.ts` `inertSiblings`: the observer inerts every body child except
  `root` itself, so if a host moves the root into a wrapper element that is a body child (for
  example a framework re-parenting it), the wrapper, and with it the open dialog, becomes inert
  and nothing on the page can be operated. Before this change the same happened only when the
  root was moved into a child that was already inert. Skipping `sibling.contains(root)` instead of
  `sibling === root` would cover it for a few bytes, if the budget allows.
- **P3** `src/core/banner.ts` observer callback: when the host removes the root the page is freed,
  but `view` stays `"banner"`; if the host later re-appends the same root, the blocking dialog is
  visible with the page not inert until the next `render`. Host-initiated and not a regression
  (previously the page stayed inert forever after removal), so advisory.
- **P3** `src/core/theme.ts`: the runtime guard checks only the `--consent-` prefix, while the
  schema also requires `[a-z0-9-]+` after it. No bypass follows (custom properties are
  case-sensitive, so `--consent-Text` is not a colour token), so this is a note only.

### Questions

- A host script that removes `inert` from body children whenever it appears would now ping-pong
  with the observer (each side's mutation triggers the other) and could keep the main thread
  busy. Is a host that fights `inert` considered out of scope, as the decision implies?
- `idPrefix` runs when the UI is built; ids the host adds later that start with the chosen prefix
  can still collide. Assumed acceptable, since the plan's entries are deferred module scripts
  that run after the body is parsed.
