# P5.1 - Linked pages stay readable

Row: `- [~] (A) P5.1 - Linked pages stay readable: the banner on a page it links to opens without backdrop, inert or focus trap, docked at the bottom (plan: Runtime behaviour, Accessibility, Size budget)`

Tier: A (blocking-mode behaviour, a public stylesheet contract, the size budget).

## Why

In blocking mode the banner's own policy link led to a page the banner covered: the backdrop dimmed
it, the page was inert, and the visitor could not read the policy before choosing, which is the
information an informed choice depends on. On a page the banner links to, the page now stays
readable: no backdrop, no `inert`, no `aria-modal`, no focus trap, and the banner is shown at the
bottom with an empty spacer of its height at the end of `body`, so the end of the policy scrolls into
view above it. The visitor still has to choose there (no close control, Escape does nothing in
blocking mode), and every other page blocks as before. A sticky in-flow banner was tried first and
dropped: on a page shorter than the viewport it floats mid-screen. The core grows by 234 bytes
gzipped, past the 6 kB budget (3 bytes were left after decision #69), so the budget becomes 6.25 kB
(decisions #70, #71).

- Docs: `docs/plan.md` (Principles 6, Runtime behaviour > Linked pages, Accessibility, Size budget),

### Findings

No P1 or P2 findings.

- **P3** `src/core/banner.ts:58-63` - the linked-page check calls `new URL(link.href, here.href)`
  unguarded. A validated config always parses, but `mount()` with an unvalidated config holding an
  unparseable href (for example `https://exa mple.com`), or a mount in an `about:srcdoc` frame with
  a relative href, now throws in `createUi`, so no banner is shown and no choice can be made, where
  before the link simply rendered. Wrapping the parse in `try { … } catch { return false; }` keeps
  the old behaviour for a few bytes.
- **P3** `src/core/banner.ts:229-233` with `src/core/theme.ts:13` - the spacer's `height` is a
  second, non-theme use of `style.setProperty` on an element outside the root. It is CSP-clean
  (property-level CSSOM, and the zero-violation e2e holds), but the theme comment "Nothing else
  touches inline style" and Principles 3 / CSP ("each theme value is applied … on the banner's
  root element") now describe less than the code does. Update the comment and add one clause to
  the CSP section naming the spacer.
- **P3** `docs/plan.md` Linked pages, decision #70 - "The settings dialog is unchanged" reads as
  "still modal", while the code and the unit test "the settings dialog does not make the page
  inert either" make it non-modal on a linked page (no `aria-modal`, no inert, no trap, no
  backdrop), as the Accessibility bullet says. Say "keeps its centred position" (or similar) so
  the two sections agree.
- **P3** `src/core/banner.ts:273-279` - the spacer is removed while the settings dialog is open,
  so a visitor scrolled to the end of the policy who opens settings sees the page shrink and the
  scroll position jump, and it does not return when settings closes back to the banner. Keeping
  the spacer while `view !== null` avoids that.
- **P3** `README.md` - `data-readable` (and that `data-blocking` is `"false"` on a linked page under
  a blocking config) is named in the plan but not in the README section a stylesheet author reads.

### Questions

- An href that resolves to every page (`#`, `#section`, `?x`, `.` on a directory page), or a
  query-routed site (`/index.php?page=privacy`, query ignored by contract), makes every page a
  linked page, so blocking mode is silently off site-wide. This follows the contract as written;
  is it worth a validation warning, or a note in the README?
- A fixed banner with no focus trap can cover page links a keyboard user tabs to mid-page
  (WCAG 2.2 Focus Not Obscured, outside the 2.1 AA target), and on a landscape phone or at high
  zoom the banner can take most of the viewport. Accepted for now, or a follow-up?

### Findings

- **P2** `src/core/banner.ts:233-239` (the ResizeObserver callback) with `render` at `:278-285` -
  the spacer stays connected while the settings dialog is open, but it no longer has the banner's
  height. `render("settings")` sets `banner.hidden`, the stylesheet makes it `display: none`, the
  ResizeObserver reports the size change and the callback sets the spacer to
  `calc(0px + 1rem)`. Requirement: decision #70 and "Changes after Review 1" item 4 state the
  spacer is kept while the settings dialog is open "so the page does not jump"; the unit test
  "the spacer stays while the settings dialog is open" checks only `isConnected`, so it passes
  against the defect. Failure scenario, measured in Chromium against the demo's `/cookies/` at
  375 x 667: scrolled to the end, spacer 305 px, `scrollHeight` 744, `scrollY` 77; after opening
  settings, spacer 16 px, `scrollHeight` 667, `scrollY` 0; after Escape back to the banner the
  spacer is 305 px again but the visitor stays at the top. That is the jump Review 1's P3
  described, and the append-only decision log would record behaviour the code does not have.
  Smallest fix: size the spacer only while the banner is shown, e.g. in the callback
  `if (!banner.hidden) spacer.style.setProperty(...)`, so the last measured height is kept while
  the settings dialog is open (a few bytes; 20 bytes of budget remain). Regression test: an e2e
  case on `/cookies/` that scrolls to the end, waits two animation frames, opens settings, waits
  two frames, and asserts `scrollY` and `scrollHeight` are unchanged and the spacer height still
  equals the banner height plus 16 px; then Escape and assert the same again. The jsdom unit test
  cannot see this, as layout and ResizeObserver are not real there.
