# P4.3 - Release workflow, release gate, releasing docs

Row: `- [~] (A) P4.3 - Release workflow with staged provenance publishing, tag/version gate, docs/releasing.md (plan: Releases)`

Tier: A (releasing)

## Why

The plan's Releases section moves publishing from "outside this repository" to a tag-driven
workflow, and decision #63 fixes its shape: a stage-only trusted publisher, no token, a
maintainer approving each version with 2FA. `release.yml` runs on `vX.Y.Z` tags, reuses
`ci.yml` as its first job so a tag is published only after the full gate passes on that commit,
and then, in a job that alone holds `id-token: write`, checks that the tagged commit is on
`main`, installs, builds, runs the release gate and stages with
`npm stage publish --provenance --access public` (npm 11.15.0 or later, installed in the job
because Node 22 ships npm 10; command and version confirmed against npm's staged-publishing
documentation). The gate stays the one TypeScript script with pure rules: it gains an optional
tag argument that must be `v` plus the `package.json` version, requires the dated changelog
entry to list at least one change, skips the clean-tree rule when `GITHUB_ACTIONS` is set, and
says to build first when the pack has no `dist/`. The build runs before the gate because the
packed-file rule needs `dist/`. `docs/releasing.md` is the per-release procedure, the
trusted-publisher setup with npm's 48-hour expiry of unused configurations, and the fix-forward
rule; unlike a common practice, a tag whose workflow failed before staging is not deleted, since
the plan never deletes a tag. A pull-request template carries the review checklist. This package
also records the P4.2 CI run URLs in that package's review file.

A tag cannot be dry-run without publishing, so acceptance is unit-test based; the real `v0.3.0`
run happens in P4.7.

The workflow matches the contract: tag-triggered only (no `workflow_dispatch`), the full CI
workflow runs first on the tagged commit, `id-token: write` exists only in the publish job, the
publish job refuses a tag that is not an ancestor of `origin/main`, then runs install, build,
release check and stage in that order, and stages with `npm stage publish` so nothing goes live
without a maintainer's 2FA approval. No token is referenced. The gate refuses a malformed or
mismatched tag (an empty `GITHUB_REF_NAME` is refused too, since `""` is not `vX.Y.Z`), an
undated or empty changelog entry, and a pack without `dist/`; the clean-tree rule is skipped only
when `GITHUB_ACTIONS` is `true`, as the plan states. Staged publishing requiring npm 11.15.0 and
an existing package agrees with npm's published documentation, and the package already exists on
npm (decision #62).

### P3

1. `.github/workflows/release.yml`, publish job: third-party actions are referenced by major tag
   and `pnpm install` runs dependency lifecycle scripts in the job that holds `id-token: write`,
   so a compromised action or dependency could mint the OIDC token and stage a version. The 2FA
   approval contains this, but pinning actions to commit SHAs (and, optionally, installing with
   `--ignore-scripts` in this job) would narrow it. `docs/releasing.md` could also tell the
   approver to confirm that exactly one staged entry exists for the version before approving.
2. `docs/releasing.md`, Fix forward: a transient failure (registry outage, runner fault) can be
   fixed by re-running the failed workflow run on the same tag, which moves nothing; saying so
   avoids burning a patch version for an infrastructure hiccup.
3. `scripts/release-check.ts`: the argv and `GITHUB_ACTIONS` wiring is covered only by the manual
   runs in the evidence, not by a test. Acceptable for a thin shim; noted.
4. `.github/PULL_REQUEST_TEMPLATE.md` is not listed in the plan's Repository layout and is outside
   the P4.3 row; its last checklist item overlaps the neutrality item above it. Consider adding
   it to the layout in a later docs change.
5. The publish job does not repeat `ci.yml`'s Node >= 22.22 guard; `node-version: 22` resolves to
   the newest 22.x, which satisfies npm's Node 22.14 requirement for staging, so this is only
   belt and braces.
