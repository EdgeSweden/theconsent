# P4.4 - Vite-based config loader with dependency watching

Row: `- [~] (A) P4.4 - Vite-based config loader with dependency watching, astro >= 5.4 (plan: Astro integration)`

Tier: A (dependencies: the Astro peer range; a public contract: what a config module may contain)

## Why

The integration loaded the config with Node's own `import()`. A `.ts` config therefore needed
Node >= 22.18 and erasable syntax, every import needed an explicit extension, JSON needed import
attributes, and `astro dev` watched only the config file, so editing an imported strings file
left the validated config stale. The config is now loaded with `runnerImport` from the Vite the
site's own Astro resolves (Vite is Astro's dependency, never ours, so no dependency is added), and the config plus every module it
imported is passed to `addWatchFile`. `runnerImport` arrives with Vite 6.1, which Astro requires from 5.4, so the optional peer
becomes `astro >= 5.4` (decision #66) and an older Astro fails with a message naming that
requirement. The claim is scoped to what is tested: TypeScript and JavaScript modules, relative
imports with or without extensions, JSON imports, installed packages. Path aliases and `.env`
values are not available because the runner is called with `configFile: false`, and a
config module that mentions `import.meta.env` is refused by a small runner plugin before Vite
replaces it (on Vite 6 and 8 alike), so it fails instead of validating a stand-in value; tests pin both limits and the README lists them. The virtual module still re-exports the config module
itself so a `record` function reaches the browser, and the page script and the `page-ssr`
stylesheet import are unchanged. A dev dependency `astro-min` (Astro 5.4.0, with Vite overridden
to 6.2.0) lets a real `astro build` of a minimal site run at the lowest supported Astro next to
the current one; the test builds the package itself so it never depends on a stale `dist/`
(decision #67). The loader lives in `./astro`, so the browser budgets are unaffected.

## Review 1

Reviewed `git diff main` plus the new files against the plan (Astro integration, Validation,
Repository layout, Safety) and decisions #34, #66 and #67. Ran `pnpm exec vitest run
test/unit/astro.test.ts test/unit/astro-build.test.ts` (29 passed), `pnpm type-check` and
`pnpm lint` (both clean), and `pnpm install --frozen-lockfile --offline` (lockfile matches
`package.json` and the `pnpm-workspace.yaml` override). Astro 5.4.0 declares `vite: ^6.2.0`, so
the `astro-min` pin to Vite 6.2.0 is the real floor of the supported range.

### Findings

**P2 - `import.meta.env` is now defined at validation time, so the validated config can differ
from the shipped one without any error.**

- Location: `src/astro/integration.ts`, `loadConfig` (the `runnerImport` call).
- Violated requirement: plan, Principles 4 ("Config is the contract") and Validation (it runs at
  build time and a failure fails the build); README: "the validated object and the shipped object
  must be the same". The old loader enforced this: under Node's `import()`, `import.meta.env` is
  `undefined`, so any use of it threw and the build failed.
- Failure scenario: Vite's module runner gives the config module
  `import.meta.env = { BASE_URL: "/", DEV: true, MODE: "development", PROD: false, SSR: true }`
  with no `.env` values (checked with `runnerImport` from the Vite that Astro 7 resolves). A
  config with `record: import.meta.env.PUBLIC_RECORD_URL ?? "/consent"` or
  `policyVersion: import.meta.env.PROD ? "2026-10" : "dev"` validates the fallback or development
  value; the browser bundle, built by the site's Vite with the site's `.env` and
  `PROD: true`, ships something else. That value never ran through `validateConfig`: for example a
  scheme-relative record URL, or a `policyVersion` over 32 characters. The README says `.env`
  values are "not available", but the build gives no sign of it.
- Smallest safe fix: pass `define: { "import.meta.env": "undefined" }` in the `runnerImport`
  inline config. Any use of `import.meta.env.X` then throws again during loading and is reported
  as `cannot load <config>: ...`. Checked by hand: with that define,
  `import.meta.env.PUBLIC_X ?? "fallback"` throws `TypeError: Cannot read properties of undefined`,
  and a config that does not use `import.meta.env` loads unchanged. Add a README sentence saying a
  config that reads `import.meta.env` fails the build.
- Regression test: in `test/unit/astro.test.ts`, a config with
  `policyVersion: import.meta.env.PUBLIC_POLICY ?? "2026-10"`, and a `.env` with `PUBLIC_POLICY`
  next to it, must reject with `/^@edgesweden\/consent: cannot load /` and must not inject a
  script. Optionally also a variant that uses `import.meta.env.PROD`.

**P3 - The reason given for watching before validation does not hold.** In both Astro 5.4 and
7 (`core/dev/restart.js`), a restart that fails keeps the previous container's `settings`, so the
watch list from the last valid load is what picks up the fix. The `addWatchFile` calls made during
a failing run are discarded, and a failure on first start ends `astro dev`. Watching early does no
harm, but the code comment, the review file's _Why_ and decision #67 ("also when validation
fails") describe a mechanism that does not exist. The test "an invalid config is still watched"
only checks the call order. Either reword the comment, or keep it and stop presenting it as the
reason a fix restarts the server.

**P3 - The README says the config is "transformed the way the browser bundle will be".** This
overclaims. The runner externalises installed packages and resolves them with Node conditions
(`node`, `module-sync`), not the browser conditions. It also gives `import.meta.env` different
values (see the P2). Suggest: "transformed by Vite (TypeScript, JSON, extensionless imports)".

### Questions

- `loadRunnerImport` resolves `astro` from the project root, not from the Astro that is running
  the hook. In a workspace where the site's root resolves a different Astro than the CLI in use,
  the runner's Vite comes from the other copy. This is probably acceptable. Is it worth a sentence
  in decision #67?

Verdict: changes required

### Findings

**P2 - `define: { "import.meta.env": "undefined" }` has no effect on Vite 6, so at Astro 5.4 to
5.x a config that reads `import.meta.env` still validates a stand-in value without error.**

- Location: `src/astro/integration.ts`, `loadConfig` (the `define` passed to `runnerImport`);
  `test/unit/astro.test.ts`, "a config that reads import.meta.env fails to load instead of
  validating a stand-in".
- Violated requirement: plan, Principles 4 and Validation; the README sentence "a config that
  reads it fails the build"; CHANGELOG ("a config that reads `import.meta.env` fails the
  build"); decision #67. All of them hold for the whole declared peer range `astro >= 5.4`.
- Failure scenario: with Vite 6.2.0, the Vite Astro 5.4.0 resolves, a config containing
  `policyVersion: import.meta.env.PUBLIC_POLICY ?? "2026-10"`, with a `.env` that sets
  `PUBLIC_POLICY` next to it, loads without error. Inside the module `import.meta.env` is
  `{ SSR: true }`, so `"2026-10"` is validated, while the browser bundle gets the `.env` value.
  `import.meta.env.PROD` gives `undefined` instead of throwing. With Vite 8.3.4 the same module
  throws as intended. The unit test only runs against the Astro dev dependency (Vite 8), so it
  passes and hides this. This is the exact failure Review 1 described, and it remains on every
  Astro 5 release (all on Vite 6) that the new peer range claims to support.
- Smallest safe fix: do not rely on `define`, whose handling of `import.meta.env` differs
  between Vite versions. Pass an inline plugin in the `runnerImport` config whose `transform`
  hook throws `import.meta.env is not available in the consent config` for any module outside
  `node_modules` whose code contains `import.meta.env`. The error then reaches the existing
  `cannot load <config>: ...` path. Keep the `define` if you want, but not as the guarantee. Or
  add a version-independent check after loading. Either way the behaviour must be the same at
  the floor of the range and at the current Astro.
- Regression test: run the `import.meta.env` test against both Astro packages. For example, in
  the temp project, link `node_modules/astro` to `astro-min` for one case, so `loadRunnerImport`
  resolves Vite 6.2.0, and leave it unlinked for the other. Cover both
  `import.meta.env.PUBLIC_POLICY ?? "…"` and `import.meta.env.PROD`. Both must reject with
  `/^@edgesweden\/consent: cannot load /` and inject no script. An `astro build` case in
  `test/unit/astro-build.test.ts` under `describe.each(["astro-min", "astro"])` would also work.

**P3 - The review file's _Why_ still says the config "is transformed the way the browser bundle
will be".** This paragraph becomes the commit body, so the claim Review 1 flagged would reach
`main`. Use the README's wording.

- P3 (_Why_ wording): resolved; the _Why_ now says the config is loaded through the runner and
  names what it supports, without the browser-bundle claim.
