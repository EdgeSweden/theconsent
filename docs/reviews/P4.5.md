# P4.5 - Validation reports schema and cross-field errors in one pass

Row: `- [~] (A) P4.5 - Validation reports schema and cross-field errors in one pass (plan: Validation)`

Tier: A (a public contract: validation rules)

## Why

`validateConfig` returned schema errors alone and ran the cross-field rules only once the shape
was valid, so a config with an unknown key and a missing locale string needed two builds to fix.
The cross-field rules now run on every input next to the schema. They read the raw input
defensively and use each part only when that part is itself well-formed: ids that match the id
pattern (so a category with an unrelated error still counts for the locale checks), non-empty
labels, parseable colours, a non-empty category list. A malformed part is therefore reported
once, by the schema, and not again by a rule that depends on it; when any category or service id
is malformed, the stray-string and unknown-mapping checks are skipped, because the misspelt id's
strings would otherwise be reported as strays (decision #68). Rules, messages and paths are
unchanged, including the `locale` key check, the empty-title rule, link-id uniqueness and the
`LATER_KEYS` hint; the existing suite passes unmodified. The returned config is still the
schema's output, and `ok` is true only when both the schema and the rules pass.

### P2

**P2-1. A category or service that is not an object brings back the stray-string errors that
decision #68 says are suppressed.**

- Location: `src/astro/validate.ts`, `crossFieldIssues`, the id loop
  (`if (!isObject(category)) return;`, `if (!Array.isArray(category["services"])) return;`,
  `if (!isObject(service)) return;`).
- Requirement: decision #68 and the CHANGELOG entry say a malformed part is reported once, by
  the schema, and that the stray-string checks are skipped while a category or service id is
  malformed. A category or service with no well-formed id is exactly that case. Today
  `malformedId` is set only when the item is an object whose `id` is bad.
- Failure scenario: `categories: [{ id: "necessary", required: true }, "analytics", …]`, a
  plausible shorthand mistake, or `categories[1] = null`. The result is
  `categories[1]: expected object` and also `locales.en.categories.analytics`,
  `locales.en.services.stats`, `locales.sv.categories.analytics` and `locales.sv.services.stats`,
  each saying "no category/service with id …". That is five errors where there should be one,
  and four of them point the author at the correct locale strings instead of at the broken
  declaration. The same happens with `services: { id: "stats" }` (an object where an array is
  expected) and with `services: ["stats"]`: one schema error, plus one stray `services.stats`
  error per locale.
- Smallest safe fix: set `malformedId = true` when a category is not an object, when
  `category["services"]` is present but not an array, and when a service is not an object.
- Regression test: in the "a malformed part is reported once, by the schema" test, add
  `categories[1] = "analytics"` → `["categories[1]"]`, `categories[1].services = {…}` →
  `["categories[1].services"]` and `categories[1].services[0] = "stats"` →
  `["categories[1].services[0]"]`.

### P3

- **P3-1. A non-string colour is replaced by the default in the contrast check.**
  `theme.colors: { background: 5, text: "#777" }` gives the schema error at
  `theme.colors.background`, plus a contrast issue at `theme.colors.text` computed against the
  default background. That issue is a warning by default and an error under
  `strictContrast: true`. An unparseable string sets `colorsParse = false` and suppresses
  contrast; a value that is present but not a string should do the same.
- **P3-2. An empty link id is reported twice.** `links: [{ id: "", … }]` gives
  `links[0].id: must not be empty` and also `{link:policy} matches no entry`. The second error is
  true, but it depends on the malformed part. It is minor and consistent with how the rules
  treat a link id; mentioned only for symmetry with the category-id rule.

### Questions

- `consentMode.extra.analytics_storage: "maybe"` together with a mapping of `analytics_storage`
  gives two errors at the same path: the schema's enum error and the ownership conflict. I read
  these as two separate problems, both worth reporting. Please confirm that this is intended.

Verdict: changes required

Implementer note after Review 1: P2-1 fixed (a category that is not an object, a `services`
value that is not an array and a service that is not an object now count as malformed ids);
P3-1 fixed (a colour that is present but not a string stops the contrast check, as an
unparseable string does); P3-2 fixed (a link without a usable id makes that locale's tokens
unresolvable, so they are not reported; the href check still runs). Regression cases added to
"a malformed part is reported once, by the schema". Question: the `extra` enum error and the
ownership conflict at the same path are two separate problems (an invalid value, and a key
claimed twice), so both are kept.

- P3-2: resolved. A link that is not an object, or has no usable id, makes that locale's tokens
  unresolvable; the href check still runs for the other links.
- Question: the answer (two distinct problems, both reported) is consistent with the plan.
