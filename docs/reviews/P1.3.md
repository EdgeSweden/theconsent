# P1.3 - Banner + settings dialog

Row: `- [~] (A) P1.3 - Banner + settings dialog: DOM, focus, blocking and non-blocking, positions (plan: Runtime behaviour, Accessibility)`

Tier: A

## Why

The banner is where Principles 1 and 2 meet the visitor: Accept all and Reject all are built
from the same function with the same classes and are always on the first layer, whatever
`buttons` says; the only way past a blocking banner is a choice, and a non-blocking close stores
nothing. All DOM is built from elements and text nodes, so the CSP rules hold without exceptions.
Every choice goes through the P1.2 runtime, so the UI cannot write or record anything the state
machine would not. The stylesheet is now built as a minified CSS entry (decision #29) because the
verbatim copy alone used a third of the size budget. Theme values and `{link:<id>}` rendering
arrive in P1.4; until then the description renders as plain text. Behaviour the plan leaves open
is settled in decisions #24 to #28.

### Findings

No P1 or P2 findings.

- **P3** `src/core/banner.ts` (category ids): the switch id `consent-category-<id>` and the
  description id `consent-category-<id>-description` can collide, because `-` is legal in
  category ids. Categories `a` and `a-description` give the second checkbox the same id as the
  first category's description `<p>`, so its `<label for>` resolves to the `<p>` and the switch
  loses its accessible name. Contrived but cheap to rule out: use a separator that the id
  pattern forbids (for example `consent-category.<id>` / `consent-description.<id>`).
- **P3** `src/core/banner.ts` `setInert`: reads `doc.body.children` without a guard. Mounting
  before `<body>` exists is supported (late-body path), but a programmatic `openSettings()` in
  blocking mode before `DOMContentLoaded` throws a TypeError, and with a valid choice the
  settings dialog would then be shown unfocused after attach. Not reachable from the Astro
  integration's deferred module script; consider making `openSettings` a no-op until the root
  is attached.
- **P3** `src/core/banner.ts` `buttonOrder`: the runtime trusts `buttons.order` verbatim, so a
  non-Astro host that calls `mount` without `validateConfig` can drop Reject all. Validation is
  where the plan enforces this, so it is not a defect, but appending any missing
  `acceptAll`/`rejectAll` at runtime would make Principle 2 hold regardless of the host for a
  few bytes.
- **P3** `src/core/banner.ts`: the settings dialog has no `aria-describedby` for
  `settingsDescription`, unlike the banner.
- **P3** `src/styles.css` `.consent__switch`: with `appearance: none` the toggle state is drawn
  only with backgrounds, which forced-colours (Windows high contrast) mode overrides; a
  `@media (forced-colors: active)` border on the track and knob would keep the state visible.

### Questions

- `layout.width` is in the schema but nothing applies it yet (the stylesheet has the
  `--consent-width` default only). Is it intended to land with the theme custom properties in
  P1.4? If so, the P1.4 brief should say so, since it is a `layout` key, not a `theme` key.
- After a first-layer choice on the auto-opened banner there is no opener, so focus falls to
  `<body>`. That matches the plan's wording; confirm this is the intended behaviour for P1.7's
  keyboard-only e2e path.
