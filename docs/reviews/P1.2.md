# P1.2 - Cookie codec + state machine + state API + DOM mirror

Row: `- [~] (A) P1.2 - Cookie codec + state machine + state API + DOM mirror (plan: Cookie, Action semantics, State API)`

Tier: A

## Why

Everything a consumer relies on (what is stored, what is reported, what is recorded) is decided
here, before any UI exists, so the privacy-relevant logic can be tested on its own. Mount reads
the cookie and nothing else; a cookie that is unparseable, from another policy version or for a
different category set means no consent. Choices go through one function that derives the action
from the transition rather than from the button, writes the cookie only for a state-establishing
or state-changing choice, and leaves a no-op without a write. Required categories are forced to
`true` at every step. The record hook (P1.5) and the UI (P1.3) attach to the internal `onCommit`
and `setUi` seams, so `openSettings()` does nothing until P1.3 registers the UI. Locale resolution
moved here because the state carries the locale (decision #18).

### Findings

**P2-1 - `data-consent="open"` click delegation is missing from the DOM mirror.**

- Location: `src/core/runtime.ts` (`start`); no test in `test/unit/state.test.ts` "DOM mirror".
- Requirement: plan, State API, DOM mirror paragraph: "Any element with `data-consent="open"`
  reopens the settings dialog (click delegation; no component needed)." The row is "... state API
  - DOM mirror", and no `docs/decisions.md` entry defers this part to P1.3 (whose row does not
    name it). Tier A requires every gap to be written down before code.
- Failure scenario: a site footer link `<a href="#" data-consent="open">Cookie settings</a>`
  never opens the dialog, even after P1.3 registers the UI, because nothing listens for the
  click; the package then ships with no non-bundled way to withdraw consent, and the next
  package's row does not carry the requirement, so it can silently fall through.
- Smallest safe fix: in `start`, register one `click` listener on `doc` that finds
  `event.target.closest('[data-consent="open"]')`, calls `preventDefault()` and `openSettings()`
  (a no-op until P1.3 calls `setUi`). Alternatively append a decision that defers it to P1.3 and
  annotate that row - but the listener is a few lines and belongs to the mirror.
- Regression test: after mount and `setUi({ openSettings: spy, close })`, a click on a nested
  child of an element with `data-consent="open"` calls `spy` once and is default-prevented; a
  click elsewhere does not; before mount nothing is registered (and no I/O happens).

**P2-2 - `readCookie` returns only the first cookie of that name, so a leftover cookie shadows the
current choice.**

- Location: `src/core/cookie.ts` `readCookie` / `readChoice`.
- Requirement: plan, Mount and Cookie: a visitor with a valid stored choice is not re-prompted
  and consumers get the stored state; `cookie.domain` / `cookie.path` are configurable.
- Failure scenario: a site that ran with the default host-only cookie later sets
  `cookie.domain: "example.com"` (or changes `cookie.path`) and bumps `policyVersion`. The old
  host-only cookie (Max-Age one year) is not overwritten by a write with a different Domain/Path,
  so `document.cookie` now holds two `consent` cookies; per RFC 6265 §5.4 equal-path cookies are
  listed oldest first. `readCookie` returns the stale one, `readChoice` yields `null`, and the
  visitor is re-prompted on every page and every new choice is written but never read back - for
  up to a year. The same happens if the old cookie is valid: an older choice is reported instead
  of the visitor's latest one.
- Smallest safe fix: have `readCookie` return every value for `name` (or have `readChoice`
  iterate them) and use the first one that decodes and passes `isCurrent`; if several are
  current, prefer the highest `t`.
- Regression test: a document cookie string with `consent=<stale p>; consent=<current p>` mounts
  with the current choice (`at` set, no re-prompt); with two current choices the newer `t` wins.

**P3-1** - `onConsent` stores listeners in a `Set`, so subscribing the same function twice fires
the immediate call twice but changes only once, and either unsubscribe removes both. Document or
wrap each registration in its own entry.

**P3-2** - `ConsentUi.close` doc comment says "after every ... choice and every no-op"; `choose`
calls it before the commit is published. Fine, but say so, since P1.3 may rely on the order
(focus return vs. listeners reacting to the change).
