# Decisions

Append-only. Never edit an entry; append a superseding one.

2026-10-20 - `main` starts with a root commit containing only `docs/plan.md`, and P0 is the first package branched from it - a branch cannot be cut from a repository with no commits (decision #1, plan: Branches and commits)
2026-10-20 - TypeScript is pinned to 6.0.x - TypeScript 7 is outside typescript-eslint's supported range (`<6.1.0`) and changes the compiler API tsup's declaration build uses (decision #2, plan: Repository layout)
2026-10-20 - The checks run locally on the installed Node 24; `engines.node` stays `>=22` - Node 24 satisfies the plan's Node 22 floor, and Astro 7 itself requires Node >= 22.22 (decision #3, plan: Checks)
2026-10-20 - The repository is a pnpm workspace whose only member besides the root is `examples/astro`, which depends on the package as `workspace:*` - the demo must consume the package the way a site would (decision #4, plan: Repository layout, Demo)
2026-10-20 - P0 ships a one-page demo and a smoke e2e test (page loads under Astro's CSP, axe clean, zero CSP violations) - `check:e2e` must run for real from P0 because there is no CI fallback; P1.7 replaces the page with the full demo (decision #5, plan: Checks, Demo)
2026-10-20 - Companion packages of pre-approved tools are added as dev dependencies: `@eslint/js`, `globals`, `eslint-config-prettier`, `@size-limit/file`, `@types/node` - each is the documented configuration or plugin package of eslint, prettier, size-limit or TypeScript, not a new tool (decision #6, plan: Safety)
2026-10-20 - The core keeps `import "./styles.css"` as an external side-effect import of the copied stylesheet, and the `.` size budget is measured with `@size-limit/file` over `dist/index.js` plus `dist/styles.css` gzipped - bundlers then ship the stylesheet as a CSP-clean asset and the budget covers "core incl. stylesheet" (decision #7, plan: No visual flash, Size budget)
2026-10-20 - Repository scripts are TypeScript files run directly by Node's built-in type stripping (`node scripts/x.ts`), so their pure parts are unit-tested and type-checked like the rest - the plan names `scripts/release-check.*` without fixing the language, and Node >= 22.18 runs erasable TypeScript natively (decision #8, plan: Releases)
2026-10-20 - `check:size` first asserts that every browser entry in `dist/` imports only its own relative files, then runs size-limit - `@size-limit/file` does not follow imports, so the size budget alone cannot prove "zero runtime dependencies" (decision #9, plan: Repository layout, Size budget)
2026-10-20 - The demo's CSP adds `default-src 'self'` to Astro's generated `script-src`/`style-src` - a request to another origin before a choice is then blocked and reported as a violation in addition to the e2e network assertion (decision #10, plan: Demo)
2026-10-20 - `validateConfig` and the `ValidationIssue`/`ValidationResult` types are exported from `@edgesweden/consent/astro`; the `.` entry re-exports only the config types - exporting it from `.` would put zod in the browser bundle, which the plan forbids (decision #11, plan: Validation, Safety)
2026-10-20 - `validateConfig(input)` returns `{ ok: true, config, warnings }` or `{ ok: false, errors, warnings }`, where each issue is `{ path, message }` and `path` names the offending key (`categories[1].id`, `locales.sv.categories.ads`, `""` for the root) - the plan requires that a failure names the key but leaves the result shape open (decision #12, plan: Validation)
2026-10-20 - Rules derived from defaults use the resolved value: `layout.backdrop: "none"` without `layout.blocking: false` fails because blocking defaults to `true` - the plan states the defaults and the blocking/backdrop rule; applying the rule only to explicit keys would let the default config contradict it (decision #13, plan: Config, Validation)
2026-10-20 - Supported theme colour syntaxes are hex, `rgb()`/`rgba()`, `hsl()`/`hsla()`, `hwb()`, `lab()`/`lch()`, `oklab()`/`oklch()`, named colours and `transparent`; `currentcolor`, `var()`, `color()` and `color-mix()` fail - contrast can only be checked for a colour with a static value. For contrast a translucent background is composited on white and a translucent foreground on its background (decision #14, plan: Validation)
2026-10-20 - Contrast is checked against the stylesheet's default palette (`src/astro/theme-defaults.ts`) for pairs where only one side is configured, and only for the pairs the plan names - a partial theme can otherwise lower contrast against an unconfigured default (decision #15, plan: Validation)
2026-10-20 - Additional structural rules: service ids use the category id pattern; `locale`, when given, is a key of `locales`; button labels, `alwaysActive`, `settingsTitle`, link labels and hrefs are non-empty; link `href`s are relative or use `http`, `https`, `mailto` or `tel`; `cookie.name` is an RFC 6265 token, `cookie.domain` a host name, `cookie.path` starts with `/` and has no `;` or whitespace; `theme.vars` keys match `--consent-[a-z0-9-]+` - each closes a way a config could render an unlabelled control, inject a cookie attribute or a script URL (decision #16, plan: Config, Validation)
2026-10-20 - `validateConfig` reports structural (schema) errors first and runs the cross-field rules only on a structurally valid config - the cross-field rules read ids, locales and colours whose shape is only known after the structural parse (decision #17, plan: Validation)
2026-10-20 - Locale resolution lands in P1.2 with the state API, because `ConsentState.locale` is part of every state; P1.4 keeps theme and `{link:<id>}` rendering. Matching against `locales` keys is exact first, then case-insensitive (decision #18, plan: Locale resolution, Package slices)
2026-10-20 - The runtime is one instance per page: after the first `mount`, any further `mount` call is a no-op whatever its document or config - the plan requires idempotency on the same document, and a second instance would split `getConsent`/`onConsent` state (decision #19, plan: Mount)
2026-10-20 - `consent:change` is dispatched on `document` at mount with the initial state and then on every change, mirroring `onConsent` - non-bundled consumers need the initial state as much as bundled ones (decision #20, plan: State API)
2026-10-20 - A stored cookie that records a required category as `false` is treated as no valid choice - required categories are always stored as `true`, so such a cookie was not written by this config (decision #21, plan: Required categories, Mount)
2026-10-20 - An `onConsent` subscriber that throws does not stop other subscribers or the choice; the error is rethrown asynchronously so it still reaches the console - one broken consumer must not leave the page half-updated (decision #22, plan: State API)
2026-10-20 - When several cookies carry the configured name, the newest one that is current for the config is used - an old cookie on another path or domain (left after `cookie.path` or `cookie.domain` changed) must not hide the visitor's current choice (decision #23, plan: Cookie, Mount)
2026-10-20 - The default `layout.position` is `bottom-center` - the plan lists the positions but not the default; a bottom-centred card covers the least content in both blocking and non-blocking mode (decision #24, plan: Config)
2026-10-20 - The settings dialog follows `layout.blocking`: in blocking mode it is `aria-modal`, traps Tab and makes the page inert like the banner; in non-blocking mode it does neither. It always has a close control that behaves like Escape: back to the banner when no valid choice exists, otherwise closed with focus returned to the opener - the plan makes modality a property of the mode and requires Escape to return to the banner when it was the opener (decision #25, plan: Accessibility)
2026-10-20 - In non-blocking mode Escape on the banner means "decide later", exactly like its close control - the plan forbids Escape only in blocking mode, and keyboard users need the same "decide later" path as pointer users (decision #26, plan: Principles 2, Accessibility)
2026-10-20 - Focus moves to the dialog element itself (`tabindex="-1"`) on open, so screen readers announce the dialog before its first control, and the stylesheet draws the focus ring on `:focus-visible` only - the plan requires focus to move to the dialog; a permanent ring around the whole dialog would be drawn on every page load (decision #27, plan: Accessibility)
2026-10-20 - In blocking mode, focus that lands outside the open dialog is moved back into it, in addition to the Tab trap and `inert` - focus can still arrive from the browser chrome or from content added after the dialog opened (decision #28, plan: Accessibility)
2026-10-20 - The stylesheet is built by tsup as its own minified CSS entry (`dist/styles.css`) instead of being copied verbatim, and `pnpm build` empties `dist/` before tsup runs - the copied file carried comments and whitespace that cost a third of the 6 KB budget, and two parallel tsup configs must not clean each other's output (decision #29, plan: Size budget, Repository layout)
2026-10-20 - `layout.width` is applied with the theme as the `--consent-width` custom property, and `theme.vars` are applied last so they can adjust any non-colour property - width is a layout key but is themed through the same CSP-clean `setProperty` path (decision #30, plan: Config, CSP)
2026-10-20 - At runtime the first layer always renders Accept all and Reject all, appending whichever an unvalidated `buttons.order` omits and dropping duplicates - `mount` can be called without `validateConfig`, and Principle 2 must hold whatever the host does (decision #31, plan: Principles 2)
2026-10-20 - Policy links open in the same tab with no `target` or `rel`, and a `{link:<id>}` token with no matching link renders as literal text - the config controls the href, validation already rejects unknown ids, and the runtime must never fail on copy (decision #32, plan: Locale resolution)
2026-10-20 - The built-in URL recorder sends the record as an `application/json` Blob via `sendBeacon` and falls back to `fetch` (`POST`, `keepalive`, `content-type: application/json`) when `sendBeacon` is missing, throws or returns `false`; a function recorder's returned promise is caught. Each recorder receives its own copy of the categories - the plan names the transports and requires failures to be swallowed but leaves the request shape open (decision #33, plan: Record)
2026-10-20 - The integration's `config` option is a path relative to the Astro project root; the module is loaded with Node's native `import()` at build time (a `.ts` config needs Node >= 22.18 type stripping and erasable syntax only), validated, and then re-exported unchanged through the virtual module `virtual:@edgesweden/consent/config` so a function `record` reaches the browser bundle - serialising the validated object would drop functions (decision #34, plan: Astro integration)
2026-10-20 - Besides the one `page` script, the integration injects a `page-ssr` import of `@edgesweden/consent/styles.css` - Astro bundles but does not link CSS imported from a `page` script, and a `page-ssr` import is Astro's way of adding a stylesheet to every page as a CSP-hashed asset; nothing is added to layouts or pages (decision #35, plan: Astro integration, No visual flash)
2026-10-20 - On a choice the runtime closes the UI, then writes and publishes the new state (attributes, `onConsent`, `consent:change`), then records - closing first means consumers never observe an open banner after a choice, and recording last means a slow or failing recorder cannot delay what the page sees (decision #36, plan: Choice, Record)
2026-10-20 - `tsconfig.json` maps `@edgesweden/consent` and `@edgesweden/consent/astro` to the sources - `check:types` covers `examples/` and runs before `check:build`, so the demo must not type-check against a stale or missing `dist/` (decision #37, plan: Checks)
2026-10-20 - The demo is built twice from the same pages: `dist/` with the blocking config and `dist-nonblocking/` with `DEMO_VARIANT=nonblocking`, which selects a second config module that only changes `layout`; e2e serves them on two local ports - the integration takes one config per site, and the config module must be identical at build time and in the browser, so the variant is chosen in `astro.config.ts`, never inside the config (decision #38, plan: Demo, Tests)
2026-10-20 - The policy-version re-prompt e2e test plants a cookie from an older `policyVersion` instead of rebuilding the demo with a bumped version - the runtime cannot tell the two apart, and one build per test would make the suite slow without adding coverage (decision #39, plan: Tests)
2026-10-20 - The demo's gated scripts (one per optional category and one for the required category), the Consent Mode `dataLayer` stub and their e2e assertions land with the adapters in P2.3 - in v0.1.x the `gateScripts` and `consentMode` keys do not exist and fail validation, so the demo cannot exercise them yet (decision #40, plan: Demo, Version boundary, Package slices)
2026-10-20 - Each adapter entry exports its named installer (`installScriptGating`, `installConsentMode`) and the same function as `install`, takes an optional document or window as a second argument for tests and non-default hosts, and is a no-op returning a no-op disposer unless its config key is set - the plan names both the shared `install(config)` shape and the specific names, and an adapter must never act on a config that did not ask for it (decision #41, plan: Adapters, Version boundary)
2026-10-20 - Adapter bundles import the core as the external relative module `./index.js` instead of bundling a copy, and the bundle-import check allows exactly that - a bundled copy would have its own runtime, so `onConsent` in the adapter would never see the state `mount` created (decision #42, plan: Adapters, Repository layout)
2026-10-20 - Script gating evaluates the placeholders present at each consent state (at install and on every change); a placeholder's `data-type` becomes the live script's `type` (for example `module`), its `nonce` is copied, and every other attribute and the text are copied verbatim - the plan requires attributes and text to be preserved but a live script needs a real type, and a nonce is hidden from `getAttribute` after load (decision #43, plan: Script gating)
2026-10-20 - Gated scripts are activated through one sequential chain in page order: each live script is inserted only after every earlier external script without `async` has fired `load` or `error`, and external scripts without `async` are inserted with `async = false` - dynamically inserted scripts are async by default and inline code runs on insertion, so without the chain a library and its inline init code race (decision #44, plan: Script gating)
2026-10-20 - When the gate is installed while `document.readyState` is `loading`, it runs one more pass at `DOMContentLoaded`; placeholders added after that wait for the next consent change, with no `MutationObserver` - a returning visitor makes no new choice, so a gate installed from `<head>` would otherwise never see the body's placeholders, while watching all DOM mutations would cost size and run on every change to the page (decision #45, plan: Script gating)
2026-10-20 - The gate waits for `load`/`error` only on an external script the browser will execute: no `nomodule` attribute, and a `data-type` that is empty, `module` or a JavaScript MIME type; a failing activation is caught so it cannot stall the chain - a script the browser skips fires neither event, so waiting on it would leave every later placeholder inert for the rest of the page (decision #46, plan: Script gating)
2026-10-20 - The Consent Mode adapter pushes `default` synchronously at install and then an `update` only when the mapped payload differs from the last one pushed (so a stored grant yields one `update` at mount, and a change that leaves every mapped key the same yields none); `extra` appears only in `default`; entries are `arguments` objects pushed onto `window.dataLayer`, which is created if missing - `default` must precede any tag, `extra` keys never change, and gtag.js reads `arguments` objects rather than arrays (decision #47, plan: Google Consent Mode v2)
2026-10-20 - `consentMode.mapping` keys must be declared category ids, in addition to the plan's one-owner rule for gtag keys - a typo in a category id would otherwise leave its keys denied forever without a build error (decision #48, plan: Validation)
2026-10-20 - The Consent Mode adapter looks up `window.dataLayer` on every push instead of holding the array it found at install, and a gtag key that is neither mapped nor in `extra` is documented as left out of `default` rather than rejected - a site snippet may reassign `window.dataLayer`, and sites legitimately use only some keys; the README tells them to map or list every key their tags read (decision #49, plan: Google Consent Mode v2)
2026-10-20 - The injected page script installs the adapters after `mount` in a fixed order, gate then Consent Mode, each imported under its `install` export - the plan requires `install` after `mount`; the order is irrelevant to behaviour because Consent Mode pushes its `default` synchronously in `install`, before any gated tag can run (decision #50, plan: Astro integration)
2026-10-20 - The P1 smoke e2e test is removed; the full suite covers everything it asserted - its loose banner-name match would also match other dialogs (decision #51, plan: Tests)
2026-10-20 - A post-release review of v0.2.0 found three defects; they are fixed forward as v0.2.1 through three added board rows (P3.1 adapter typings, P3.2 module-script order in the gate, P3.3 Astro ClientRouter support), and ClientRouter is supported rather than documented as unsupported (maintainer's choice) - tags are never moved, and each fix touches a Tier A surface (decision #52, plan: Releases, Board)
2026-10-20 - tsup builds the browser entries (`.`, `./gate`, `./gtag`) and `./astro` as two separate builds, adapters take their types from the core entry, and `check:size` also type-checks the packed tarball from a temporary consumer that has zod but not Astro - with one build the declaration bundler routed the adapters' `ConsentConfig` through `astro.d.ts`, which imports the optional peer (decision #53, plan: Repository layout, Adapters)
2026-10-20 - Gating promises the order a page without gating would have, not one sequence across script kinds: classic scripts run in page order (the gate waits for each earlier external classic script without `async`), modules run in page order among themselves (inserted with `async = false`, which browsers order; never waited for, since an inline module fires no `load`), and `nomodule` applies to classic scripts only - natively modules are deferred, so a classic script after a module runs first; the v0.2.0 README's single "page order" claim overstated this, while the v0.2.0 runtime already behaved natively in Chromium (decision #54, plan: Script gating)
2026-10-20 - Supersedes the `async = false` part of decision #44: gated classic scripts are inserted with `async = true` and ordered only by the gate's chain, and only modules use `async = false` - an `async = false` classic script joins the browser's in-order list behind any earlier module, so a slow or never-loading module would hold up every later classic script, which an ungated page does not do (decision #55, plan: Script gating)
2026-10-20 - ClientRouter support stays inside the existing API: the core and the gate listen for Astro's `astro:after-swap` on `document`; the core then destroys the old UI (including its document listeners), re-resolves the locale from the new `<html lang>`, builds and attaches a new UI to the new `<body>` (showing the banner if no valid choice exists) and re-applies the `data-consent-*` attributes, without calling `onConsent` subscribers or dispatching `consent:change` since consent did not change; the gate rescans, and an external gated script is loaded at most once per document while inline gated code runs on each page like Astro's own inline scripts - a patch release must not add public API, and re-loading a vendor script on every navigation would duplicate it (decision #56, plan: Astro integration, Runtime behaviour, Script gating)
2026-10-20 - The demo gains a third build, `DEMO_VARIANT=router` into `dist-router/`, with Astro's ClientRouter and no CSP, served on its own port for e2e - Astro's CSP support does not cover the ClientRouter, and the main demo keeps its strict CSP (decision #57, plan: Demo, Tests)
2026-10-20 - Supersedes the gate part of decision #56: the gate rescans on `astro:page-load` (after the router has run the new page's scripts) instead of `astro:after-swap`, marks every live script it inserts with `data-astro-exec` so the router never runs it again, and records an external URL as loaded only when its live script is inserted; a URL is loaded at most once per document, also when two placeholders on one page name it. `getConsent().locale` follows the page after a swap without an `onConsent` call, since consent did not change - activating during `after-swap` let the router re-run the new script (one request, two executions), and recording at queue time let a swap block a URL for the rest of the session (decision #58, plan: Script gating, Astro integration)
2026-10-20 - Supersedes decision #55's mechanism: the gate no longer sets `async` on classic scripts at all (an inserted classic script is already async by default and stays out of the browser's in-order list without the attribute), and sets `async = false` only on a module that has no `async` attribute; `data-astro-exec` is documented as the one attribute a live script gains, and the 0.2.1 CHANGELOG wording is corrected in place - setting `.async = true` adds a visible `async` attribute, which broke the "same attributes" promise; a P3.4 board row was added for this fix-forward as v0.2.2 (decision #59, plan: Script gating, Releases)
2026-10-21 - The repository goes public as `EdgeSweden/theconsent` with CI (`ci.yml` running the check gate on every push and pull request), pull requests squash-merged into a protected linear `main`, and tag-driven staged publishing (`release.yml`); git is read-only for implementers and agents, and maintainers commit, merge, push and tag - supersedes the local-only delivery mode and decision #1's premise that git has no remote (decision #60, plan: Delivery, Checks, Releases)
2026-10-21 - The package is developed and published from the public repository EdgeSweden/theconsent under the MIT licence; package.json repository, homepage and bugs point there - the repository goes public with this decision (decision #61, plan: What this is, Releases)
2026-10-21 - 0.3.0 is the first version of this codebase published to npm; the 0.1.0–0.2.2 entries in CHANGELOG.md are local milestones that were tagged but never published, and npm versions below 0.3.0 were published from an earlier implementation of the same contract, which the 0.3.0 changelog entry says in one paragraph - a reader of npm must be able to tell the two apart (decision #62, plan: Releases)
2026-10-21 - The npm package is published only through the release workflow via a stage-only GitHub Actions trusted publisher (repository EdgeSweden/theconsent, workflow release.yml, no environment), approved by a maintainer with 2FA; the configuration is created immediately before the first release tag because npm expires an unused configuration after 48 hours - no long-lived token exists anywhere (decision #63, plan: Releases)
2026-10-21 - The size budget stays 6 kB gzipped for the core including its stylesheet and 1 kB per adapter (decision #64, plan: Size budget)
2026-10-21 - The public repository starts at the 0.2.2 import: one initial commit of the tree, with the local history and the milestone tags v0.1.0–v0.2.2 kept by the maintainer and never pushed, so v0.3.0 is the first public tag - the tag rules apply to the repository a tag is pushed to, and the local milestones were never published (decision #65, plan: Releases)
2026-10-21 - astro is an optional peer dependency >= 5.4 because the integration loads the config through Vite's runnerImport, which Astro requires from 5.4 (decision #66, plan: Astro integration)
2026-10-21 - Supersedes the loading part of decision #34: the integration loads the config module with `runnerImport` from the Vite that the site's Astro resolves (`configFile: false`, so the site's aliases and `.env` are not applied), watches the config and every module it imported, refuses (through a runner plugin that runs before Vite's own replacement, on every supported Vite) a config module outside `node_modules` that mentions `import.meta.env`, so it fails to load rather than validating a value the browser bundle would not ship, resolves Astro (and through it Vite) from the project root, and accepts an absolute config path; a dev dependency `astro-min` pins Astro 5.4.0 with Vite 6.2.0 so a real build is tested at the lowest supported version - Node's `import()` needed Node >= 22.18 and explicit extensions for a `.ts` config and watched only the config file, so an edited strings file went stale in `astro dev` (decision #67, plan: Astro integration, Tests)
